# Booking API

![CI](https://github.com/bkbe4ka/MyAPI_for_testing/actions/workflows/ci.yml/badge.svg)

REST API бронирования на FastAPI + PostgreSQL, разработанный **вместе с тестовым
фреймворком** для практики API-тестирования.

Ключевая идея проекта: спецификация фиксируется в [SPEC.md](SPEC.md) **до** реализации,
тесты пишутся по спецификации, а не по коду. Так тесты проверяют требования,
а не то, что получилось.

---

## Быстрый старт

```bash
cp .env.example .env          # заполнить значения
docker compose up -d
docker compose exec api alembic upgrade head
```

| Что | Адрес |
|---|---|
| API | http://localhost:8000 |
| Swagger UI | http://localhost:8000/docs |
| OpenAPI-схема | http://localhost:8000/openapi.json |
| Health-check | http://localhost:8000/health |

### Запуск тестов

```bash
python -m venv .venv
.venv\Scripts\activate            # Windows
pip install -r requirements-dev.txt

pytest -v
```

### Контрактное тестирование

```bash
st run http://localhost:8000/openapi.json \
  --mode all \
  --seed 42 \
  --phases examples,coverage,fuzzing
```

## Тест-стратегия

### Что покрыто и чем

| Уровень | Инструмент | Что проверяет |
|---|---|---|
| Структура и типы ответов | Pydantic-модели (`strict`, `extra=forbid`) | контракт целиком одной строкой |
| Позитивные сценарии | ручные тесты | создание, чтение, состояние в БД |
| Границы и негатив | параметризованные тесты | обязательные поля, диапазоны, типы |
| Пограничные входные данные | Schemathesis | то, что не приходит в голову вручную |
| Целостность данных | прямые запросы к БД | отсутствие побочных эффектов при ошибке |

### Три слоя моделей — и зачем они разные

| Модель | Файл | Назначение |
|---|---|---|
| SQLAlchemy | `app/models.py` | как данные лежат в БД |
| Pydantic (сервис) | `app/schemas.py` | что API принимает и отдаёт |
| Pydantic (тесты) | `tests/models/` | независимая проверка контракта |

Третья существует отдельно намеренно: если тесты используют схемы приложения,
они проверяют реализацию, а не требования. Расхождение между `tests/models/`
и фактическим ответом — сигнал об изменении контракта.

### Строгость моделей в тестах

```python
model_config = ConfigDict(extra="forbid", strict=True)
```

- `strict=True` — отключает приведение типов. `"123"` в поле `int` становится
  ошибкой, а не молча превращается в число.
- `extra="forbid"` — недокументированное поле в ответе роняет тест.
  Так ловятся утечки внутренних полей и незаявленные изменения контракта.

Исключение — поля дат. JSON не имеет типа «дата», всё приходит строками,
поэтому для них конвертация разрешена точечно.

### Изоляция

Каждый тест готовит свои данные и убирает за собой. Cleanup живёт в фикстуре
после `yield` — так он отрабатывает даже при падении теста, чего не было бы
при уборке в конце тестовой функции.

### Что сознательно не автоматизировано

- **Нагрузочные характеристики** — отдельная задача и другой инструментарий
  (Locust / k6). Функциональные тесты для этого не предназначены.
- **Полный перебор комбинаций валидации** — покрывается property-based тестами
  Schemathesis дешевле, чем ручным перебором.
- **Stateful-фаза Schemathesis** — отключена из-за ошибки инструмента
  при построении графа переходов. Причина зафиксирована
  в [docs/schemathesis-findings.md](docs/schemathesis-findings.md).

## Валидация: защита в глубину

Ограничения продублированы на трёх уровнях, и это осознанное решение,
а не дублирование по недосмотру.

| Уровень | Что даёт |
|---|---|
| Pydantic-схема | внятная ошибка 422 с указанием поля |
| Check-constraints в БД | защита от записи мимо API — миграции, ручные правки, другой сервис |
| Обработчик `SQLAlchemyError` | любая непойманная ошибка данных → 422, а не 500 |

Причина многоуровневости: **валидация не должна быть слабее самого строгого
ограничения ниже по стеку.** Разница между слоями превращается в 500-е —
именно так были найдены два дефекта (см. ниже).

## Найденные и исправленные дефекты

Все найдены Schemathesis на собственном сервисе, каждый закрыт
регрессионным тестом.

| # | Симптом | Корневая причина | Исправление |
|---|---|---|---|
| 1 | `totalprice: 176088427998661` → 500 | Pydantic допускал любое целое, PostgreSQL `INTEGER` — до 2 147 483 647 | `Field(le=2_147_483_647)` + обработчик `DataError` |
| 2 | NUL-байт в строке → 500 | PostgreSQL не хранит `\x00` в `varchar`; ошибка драйвера возникала до обёртки SQLAlchemy | `field_validator` с проверкой на входе |
| 3 | `checkin: 0` → 201, сохранено `1970-01-01` | Pydantic конвертировал число в дату как Unix timestamp | `field_validator(mode="before")` — проверка типа до конвертации |
| 4 | 404 не документирован в схеме | `HTTPException` внутри функции не попадает в OpenAPI | `responses={404: {...}}` в декораторе |
| 5 | Дублирующийся эндпоинт без ведущего слэша | опечатка при правке | удалён |

Полный разбор с командами воспроизведения и вердиктами —
в [docs/schemathesis-findings.md](docs/schemathesis-findings.md).

### Ложные срабатывания и их обоснование

Не каждая находка инструмента — дефект. Наблюдение становится дефектом,
только когда противоречит требованию.

- **`checkout > checkin` отвергается на схемно-валидных данных.**
  JSON Schema не выражает зависимости между полями. Правило задокументировано
  в `description` операции, в конфиге разрешён статус 422.
- **`GET /bookings/0` возвращает 404.**
  Схема описывает валидность идентификатора, но не существование ресурса.
  404 — корректный ответ.

## CI

Пайплайн на каждый push и pull request в `main`:

1. поднять PostgreSQL (`services` с healthcheck)
2. установить зависимости
3. применить миграции
4. запустить API и дождаться готовности `/health`
5. `pytest`
6. `schemathesis`

Ценность не в автоматизации как таковой, а в **проверке воспроизводимости**:
зелёный пайплайн означает, что проект собирается с нуля на чистой машине.
Красный — что-то держится на локальном состоянии.

## Практические выводы

Что оказалось важнее теории:

- **Тест проверяет только то, что выражено ассертом.** `print` и `if` вместо
  `assert` дают тест, который зелёный при сломанном сервисе.
- **Статус-код проверяется до парсинга тела.** При 500 тело часто не JSON,
  и `.json()` падает с ошибкой, уводящей расследование в сторону.
- **Падение в фикстуре — это ERROR, а не FAILED.** Отдельный аргумент за вынос
  подготовки в фикстуры: сломанный setup становится видимым.
- **Сообщение ассерта должно относиться к проверяемому объекту.** Подставленное
  не то тело ответа приводит к неверным гипотезам.
- **Наблюдение становится дефектом только при расхождении с требованием.**
  Без ссылки на спецификацию или стандарт баг-репорт не имеет силы.
